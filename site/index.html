Get the skill ↗

Make it local.

Clone the skill into your Codex skills folder, then invoke $estudio-godot. You stay the Director; the main session coordinates production.

Install the skill

git clone https://github.com/gafapa/estudio-godot.git "$HOME/.codex/skills/estudio-godot"

Already have that folder? Update its existing Git checkout or compare and merge your local copy.

Bring your tools

  • Godot 4, installed locally
  • Python 3.10+, Git and Bash
  • Compatible GdUnit4 for engine tests
  • A host that supports your chosen agents

The skill installs a project workflow. It does not download Godot, addons or model access.

Define the project

Save a configuration as config.json. Use your actual installed Godot version; this is a 2D example.

{
  "game": "My Game",
  "godot_version": "4.7.2",
  "dimension": "2D",
  "platforms": "PC",
  "mode": "automatic"
}

Preview, then install

python scripts/instalar.py \
  --config config.json \
  --destination ../my-game --dry-run

python scripts/instalar.py \
  --config config.json \
  --destination ../my-game

Run from the cloned skill folder. Existing project files and hooks are preserved. Personalize the result before production.

Playable, then better.

The prototype tests the central mechanic before the project grows. Milestones carry it through a vertical slice, alpha, beta and authorized release.

  1. Research & define

    Choose references, player decisions and a small prototype. Keep the design brief enough to guide the next change.

  2. Build a small slice

    Assign scoped tickets with clear ownership. Use focused tests during development and complete tests before delivery.

  3. Review the evidence

    Review the exact committed SHA. Reuse matching machine results; independently inspect and reproduce the required behavior.

  4. Integrate & play

    Integrate sequentially, validate the integrated commit afresh and inspect what changed. Playtest the actual loop.

Leave room to work.

Engine tests run headless and silent where suitable. Each bounded run closes its owned process tree, verifies closure, releases its machine lease and pauses for five seconds.

Other applications get a turn. Existing engines are left untouched. A genuine rendering check can use a bounded offscreen capture; headless results never stand in for visual proof.

Before you begin.

Can it work on an existing game?

Yes. The workflow inspects the project and preserves appropriate architecture, files and hooks. Review preserved entries and merge intended updates rather than reinstalling over your work.

Does it run a studio automatically?

The main session coordinates available tools and authorized agents. Model access and delegation depend on your host. A session hook is a reminder, not a scheduler; the skill does not continue after a closed session.

What stays under my control?

The game's vision, scope and creative direction. Publication, spending and destructive changes require existing or newly given authorization. Documentation and code are English; player-facing localization follows the game.

How do faster checks stay useful?

Focused checks shorten development feedback. Matching successful machine evidence can be reused for up to 24 hours. Ownership checks rerun, critical delivery and integrated commits use fresh validation, and reviewers retain independent judgment.
